## 1. Source of truth (DO NOT CREATE A SECOND ONE)

- `db/schema.sql:1` is the **canonical Postgres schema** (552 lines, all enums/types/tables/triggers/RLS/views). It is what `apps/api/README.md:217` calls *source of truth*.
- `supabase/migrations/20260821123132_init_smartkasi.sql:1` is a **verbatim copy** of `db/schema.sql` for the Supabase CLI (`supabase/config.toml:59-64`). SHA256 verified `E2BFAF...` on 2026-08-22 — `git diff --stat` shows they match.
- `supabase/seed.sql:1` is a **verbatim copy** of `db/seed.sql` (`55A235...`) so `supabase/config.toml:66-71` `sql_paths = ["./seed.sql"]` works for `supabase db reset`.
- `apps/api/prisma/schema.prisma:1` is **derived** — generated by `npx prisma db pull` after applying `db/schema.sql`. Never hand-edit then migrate.

**Rule:** Edit `db/schema.sql` first. Then mirror it. Then pull Prisma. Never `prisma migrate dev` — `apps/api/prisma.config.ts:10` exists but `prisma/migrations/` is intentionally empty.

## 3. Workflow for every schema change (MANDATORY)

```powershell
# 1. Edit canonical schema
code db/schema.sql

# 2. Mirror to Supabase CLI (keeps local `supabase db reset` working)
Copy-Item db/schema.sql supabase/migrations/$(Get-Date -Format yyyyMMddHHmmss)_<name>.sql -Force
# OR for initial migration: Copy-Item db/schema.sql supabase/migrations/20260821123132_init_smartkasi.sql -Force
# If you edited enums/checks/RLS that Prisma can't express, the copy MUST be verbatim.

# 3. If seed changed
Copy-Item db/seed.sql supabase/seed.sql -Force

# 4. Apply + verify locally (requires Docker Desktop)
npx supabase db reset   # or npm run supabase:reset (root package.json:12)
npx supabase status     # DB 54322 per supabase/config.toml:35, Studio 54323, API 54321

# 5. Regenerate Prisma (db/schema.sql → prisma/schema.prisma)
cd apps/api
npx prisma db pull   # uses DIRECT_URL 5432 per prisma.config.ts:18, NOT 6543
npx prisma generate  # writes apps/api/src/generated/prisma (importFileExtension="" per schema.prisma:21)

# 6. If you added a NEW migration file (not just overwriting init), use CLI naming:
npx supabase migration new add_<feature>  # or npm run supabase:migration:new
# Then put ONLY the delta in that file, not the full schema.
```

**Never:**
- Create `apps/api/prisma/migrations/` via `prisma migrate` — two sources of truth drops triggers (`db/schema.sql:443-490`).
- Edit `supabase/migrations/*.sql` without editing `db/schema.sql` — drift → `supabase db diff` shadow DB (`supabase/config.toml:37` `shadow_port=54320`) diverges.
- Write seed data directly to `supabase/seed.sql` only — always start from `db/seed.sql:1` (has `on conflict do nothing` + `do $$` idempotency guard `193-197`).

## 4. Local CLI expectations

- `supabase/config.toml:5` `project_id = "SmartKasi"` (capitalized, CLI normalizes)
- `supabase/config.toml:42` `major_version = 17` must match remote `SHOW server_version;` (header in `db/schema.sql:6` says 15+ — keep in sync)
- `supabase/config.toml:44` `pooler.enabled = false` locally — local `DATABASE_URL` is direct `54322`, not `6543/5432` pooler (`apps/api/.env.example:16-17`)
- `supabase/config.toml:409-413` `experimental.pgdelta.enabled = true` — diff engine for `supabase db diff`
- `package.json:9-16` root scripts `supabase:start|stop|reset|status|types|migration:new|diff` are thin wrappers over `npx supabase` (package `supabase@2.115.0` is the CLI, not `@supabase/supabase-js`)
- Docker **must** be running for any `--local` command (`supabase start` → Postgres 54322, Studio 54323, Inbucket 54324)

## 5. Remote vs local divergence (2026-08-22 state)

- Remote project `wndilblmkkdyzpffmwap` (eu-west-1, per `README.md:72`) was populated via `apps/api/scripts/sql.mjs:28` on `DIRECT_URL` (session pooler 5432) — **not** via `supabase db push`. So remote `supabase_migrations` table is empty or has stale hash.
